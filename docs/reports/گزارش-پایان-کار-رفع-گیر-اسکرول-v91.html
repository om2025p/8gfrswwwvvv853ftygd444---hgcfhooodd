⚠️ ریشهٔ اصلی: یک تایمر بی‌گناه به‌نظر

در صفحهٔ «دیدبان درصدها» کدی وجود داشت که هر ۳۰ ثانیه کل کارت‌ها را پاک و از نو می‌ساخت. این عملیات روی پردازندهٔ ۶ برابر کندتر (شبیه‌سازی گوشی واقعی) ۲۳۰ میلی‌ثانیه طول می‌کشد. اگر این ۲۳۰ میلی‌ثانیه وسط اسکرول کاربر بیفتد، دقیقاً همان «گیر» حس می‌شود — و چون هر ۳۰ ثانیه تکرار می‌شود، کاربر فکر می‌کند «بعد از چند ثانیه خودش رفع شد».

روش کار — چطور مقصر را پیدا کردیم

حدس زدن در این حوزه بی‌فایده است. مرورگر بدون پردازندهٔ کند همه‌چیز را «سالم» نشان می‌دهد، چون لپ‌تاپ توسعه‌دهنده چند برابر سریع‌تر از گوشی کاربر است. بنابراین از یک روش چهار مرحله‌ای تکرارپذیر استفاده شد:

مرحلهٔ ۱ — ابزارسازی

مرورگر Chromium به‌صورت برنامه‌نویسی‌شده (Puppeteer) اجرا شد و شاخص TaskDuration از رابط Performance.getMetrics() خوانده شد. این شاخص مجموع زمانی است که پردازندهٔ اصلی صرف اجرای جاوااسکریپت، محاسبهٔ استایل و چیدمان کرده است.

مرحلهٔ ۲ — کندسازی مصنوعی پردازنده

Emulation.setCPUThrottlingRate({ rate: 6 })

بدون این مرحله، تمام گزینه‌ها «سالم» به‌نظر می‌رسند. با ضریب ۶، رفتار گوشی میان‌رده شبیه‌سازی می‌شود و تفاوت‌ها آشکار می‌گردند.

مرحلهٔ ۳ — حذف تک‌تک مظنون‌ها

برای هر ویژگی مشکوک، یک استایل موقت با !important تزریق شد که فقط همان ویژگی را خاموش می‌کرد، و اندازه‌گیری تکرار می‌شد. این روش «حذف تک‌متغیره» است و اجازه می‌دهد سهم هر عامل جداگانه سنجیده شود.

مرحلهٔ ۴ — میانه به‌جای یک اجرا

هر حالت ۵ تا ۷ بار اجرا شد و میانه گزارش شد، نه میانگین و نه اولین اجرا. سیستم‌عامل در پس‌زمینه کار می‌کند و یک اجرای تنها هرگز قابل اعتماد نیست.

عامل ۱ — تایمر ۳۰ ثانیه‌ای که کل صفحه را بازسازی می‌کرد

کد معیوب (قبل)

setInterval(() => {
    resetMonitorCache();
    renderMonitor();          // کل innerHTML پاک و از نو ساخته می‌شود
}, 30000);               // هر ۳۰ ثانیه، بی‌قید و شرط

هزینهٔ اندازه‌گیری‌شده

سنجهمقدارتوضیح

کد اصلاح‌شده (بعد)

// بازسازی کامل ~۲۳۰ms طول می‌کشد و اگر وسط اسکرول اجرا شود «گیر» می‌دهد.
// پس فقط وقتی تب دیده می‌شود و فقط اگر دادهٔ localStorage واقعاً عوض شده
// باشد دوباره رندر می‌کنیم.
var monitorDataSignature = null;

function computeMonitorSignature() {
    var parts = [];
    try {
        for (var i = 0; i < localStorage.length; i++) {
            var k = localStorage.key(i);
            if (!k || k.indexOf('emarat_') === 0) continue;
            var v = localStorage.getItem(k) || '';
            parts.push(k + ':' + v.length);
        }
    } catch (e) {}
    return parts.sort().join('|');
}

monitorDataSignature = computeMonitorSignature();

setInterval(function () {
    if (document.visibilityState !== 'visible') return;  // تب پنهان = هیچ کاری
    var sig = computeMonitorSignature();
    if (sig === monitorDataSignature) return;            // داده عوض نشده = هیچ کاری
    monitorDataSignature = sig;
    resetMonitorCache();
    renderMonitor();
}, 30000);
✅ نتیجه

در حالت عادی (کاربر فقط اسکرول می‌کند و داده عوض نمی‌شود) این تایمر هیچ کاری نمی‌کند. وقتی کاربر از تب دیگری برمی‌گردد و داده عوض شده، یک‌بار رندر می‌شود — همان رفتار مورد انتظار، بدون مسدودسازی بی‌مورد.

عامل ۲ — انیمیشن بی‌نهایت روی box-shadow

کارت هوش مصنوعی یک درخشش طلایی داشت که هر ۴ ثانیه تکرار می‌شد. مشکل اینجاست که box-shadow یک ویژگی رنگ‌آمیزی است: تغییر آن باعث می‌شود مرورگر در هر فریم آن ناحیه را از نو نقاشی کند. اگر روی همان کارت backdrop-filter هم باشد، هر فریم باید یک بلور جدید محاسبه شود.

کد معیوب (قبل)

.ai-glass-card {
    background: #000000 !important;
    backdrop-filter: blur(20px);      /* روی سیاهِ خالص = بی‌اثر بصری، گران فنی */
    animation: pulseGlowGold 4s infinite ease-in-out;
}

@keyframes pulseGlowGold {
    0%, 100% { border-color: ...; box-shadow: 0 0 20px rgba(...); }
    50%      { border-color: ...; box-shadow: 0 0 35px rgba(...); }
}

کد اصلاح‌شده (بعد)

.ai-glass-card {
    background: #000000 !important;
    /* backdrop-filter حذف شد: پس‌زمینه کاملاً کدر است، پس بلور هیچ چیزی
       برای بلور کردن ندارد و فقط هزینهٔ ترکیب‌بندی می‌سازد. */
    position: relative;
    isolation: isolate;
}

/* درخشش به یک لایهٔ مجزا منتقل شد. فقط opacity انیمیت می‌شود که
   کامپوزیتور انجامش می‌دهد — بدون نقاشی مجدد. */
.ai-glass-card::after {
    content: '';
    position: absolute;
    inset: -1px;
    border-radius: inherit;
    border: 1px solid rgba(245, 158, 11, 0.85);
    box-shadow: 0 0 35px rgba(245, 158, 11, 0.45);
    opacity: 0.35;
    pointer-events: none;
    z-index: -1;
    animation: pulseGlowGold 4s infinite ease-in-out;
    will-change: opacity;
}

@keyframes pulseGlowGold {
    0%, 100% { opacity: 0.2; }
    50%      { opacity: 0.85; }
}
💡 چرا opacity ارزان است؟

مرورگر می‌تواند لایه‌ای که فقط شفافیتش عوض می‌شود را به پردازندهٔ گرافیکی بسپارد. سایه و حاشیه یک‌بار نقاشی می‌شوند و بعد فقط ضریب شفافیت تغییر می‌کند. نتیجه: ظاهر تقریباً یکسان، هزینهٔ نزدیک به صفر.

عامل ۳ — backdrop-filter روی پس‌زمینهٔ کدر

این یک اشتباه منطقی است، نه فقط فنی. backdrop-filter محتوای پشت عنصر را بلور می‌کند. اگر پس‌زمینهٔ خود عنصر کاملاً کدر باشد (#000000)، هیچ محتوایی از پشت دیده نمی‌شود — پس بلور کردنش هیچ تغییری در تصویر ایجاد نمی‌کند. اما مرورگر همچنان هزینهٔ محاسبه را می‌پردازد.

🎭 تشبیه ساده

مثل این است که عینک ته‌استکانی بزنی و به یک دیوار سیاه نگاه کنی. عینک کار می‌کند، اما چون چیزی پشتش نیست، تصویری که می‌بینی دقیقاً همان دیوار سیاه است. تنها چیزی که عوض می‌شود، خستگی چشم است.

درمان: حذف کامل backdrop-filter از هر عنصری که پس‌زمینهٔ آن کدر است.

عامل ۴ — انیمیشن transform روی ظرف ۲۳۰۰ پیکسلی

بخش فعال صفحهٔ دیدبان ارتفاعی حدود ۲۲۸۷ پیکسل دارد. انیمیشن ورود آن از transform: translateY(10px) استفاده می‌کرد. مشکل: وقتی مرورگر transform را روی یک عنصر انیمیت می‌کند، آن عنصر را به یک لایهٔ ترکیب‌بندی جداگانه ارتقا می‌دهد. این لایه بعد از پایان انیمیشن هم باقی می‌ماند و برای یک عنصر ۲۳۰۰ پیکسلی، حافظهٔ گرافیکی قابل توجهی مصرف می‌کند.

کد معیوب (قبل)

.content-section {
    animation: fadeIn 0.4s ease forwards;
}
@keyframes fadeIn {
    from { opacity: 0; transform: translateY(10px); }
    to   { opacity: 1; transform: translateY(0); }
}

کد اصلاح‌شده (بعد)

.content-section.active {
    display: block;
    animation: fadeIn 0.3s ease;   /* فقط روی بخش فعال */
}
@keyframes fadeIn {
    from { opacity: 0; }
    to   { opacity: 1; }
}

/* احترام به تنظیم کاهش حرکت کاربر */
@media (prefers-reduced-motion: reduce) {
    .content-section.active { animation: none; }
}

عامل ۵ — background-attachment: fixed در «رد پای من»

این ویژگی باعث می‌شود پس‌زمینه هنگام اسکرول ثابت بماند. اما پیاده‌سازی آن در مرورگرهای موبایل به این معناست که در هر فریم، کل ویوپورت باید از نو رنگ آمیزی شود — چون مرورگر نمی‌تواند پس‌زمینه را یک‌بار نقاشی کند و جابه‌جا کند.

کد اصلاح‌شده (بعد)

/* گرادیان پایه روی body می‌ماند (بدون attachment) */
body {
    background: linear-gradient(180deg, #0b1424 0%, #0e1c2e 55%, #0a1220 100%);
}
/* هاله‌های رنگی روی یک لایهٔ ثابت جداگانه — یک‌بار نقاشی، همیشه ثابت */
body::before {
    content: '';
    position: fixed;
    inset: 0;
    background:
        radial-gradient(900px 420px at 85% -8%, rgba(94,234,212,.13), transparent 62%),
        radial-gradient(760px 380px at 6% 0%, rgba(255,209,102,.10), transparent 60%);
    pointer-events: none;
    z-index: -1;
}

علاوه بر این، backdrop-filter: blur(9px) از کارت‌های آمار و بخش‌ها حذف شد و در عوض کدری پس‌زمینهٔ کارت از ۸۲٪ به ۹۲٪ افزایش یافت تا ظاهر بصری حفظ شود.

در جریان کار، دو نوع اندازه‌گیری انجام شد و نتیجه‌شان متفاوت بود. این تفاوت مهم است و پنهانش نمی‌کنیم:

  • اندازه‌گیری اول (تک‌دوره‌ای): برای صفحهٔ دیدبان اعداد ۷۶ و ۷۷ میلی‌ثانیه به‌دست آمد — یعنی «بدون تفاوت». این نتیجه گمراه‌کننده بود.
  • اندازه‌گیری دوم (متقاطع A/B، سه دور): همان صفحه ۳۱۶ در برابر ۱۱۵ میلی‌ثانیه نشان داد — یعنی ۲٫۷۶ برابر بهتر.

چرا تفاوت؟ چون هزینهٔ اصلی (تایمر ۳۰ ثانیه‌ای) تصادفی است. فقط اگر تایمر دقیقاً در بازهٔ اندازه‌گیری بیفتد ظاهر می‌شود. یک دور اندازه‌گیری شانس دیدنش را ندارد؛ سه دور متقاطع دارد.

بنابراین سنجهٔ قابل‌اعتماد، هزینهٔ مستقیم renderMonitor() است که مستقل از شانس و نویز اندازه‌گیری شد:

بخش ۶

درس‌های آموخته‌شده

۶.۱ — فرضیهٔ اول همیشه غلط است

اولین حدس این بود که «دکمهٔ به‌روزرسانی» مقصر است، چون تازه اضافه شده بود و روی هر صفحه حضور داشت. اندازه‌گیری این فرضیه را رد کرد: حذف کامل دکمه فقط ۶ میلی‌ثانیه تفاوت داد. مقصر واقعی یک تایمر و دو انیمیشن قدیمی بودند.

🎯 قاعده

هرگز بر اساس «چه چیزی تازه تغییر کرده» قضاوت نکن. بر اساس «چه چیزی اندازه‌گیری می‌شود» قضاوت کن.

۶.۲ — بدون کندسازی پردازنده، همه‌چیز سالم به‌نظر می‌رسد

در مرورگر بدون محدودیت، هزینهٔ اسکرول هر دو صفحه حدود ۱۶ میلی‌ثانیه بود — یعنی ۶۰ فریم بر ثانیهٔ کامل. اگر فقط با این عدد قضاوت می‌کردیم، نتیجه می‌گرفتیم «هیچ مشکلی نیست» و کاربر همچنان گیر می‌دید. ضریب ۶ پرده را برداشت.

۶.۳ — «بعد از چند ثانیه خودش درست می‌شود» نشانهٔ تایمر است

این جملهٔ کاربر طلایی بود. اگر مشکلی با اسکرول رفع می‌شد، علتش چیدمان بود. اگر با گذشت زمان رفع می‌شد، علتش یک تایمر بود. جست‌وجو در کد یک setInterval با فاصلهٔ ۳۰ ثانیه را لو داد.

۶.۴ — ابزار اندازه‌گیری، بخشی از محصول است

برای اینکه این مشکل برنگردد، قانون اسکرول در AGENTS.md مستند شد و بازرس خودکار check-refresh-button.py در مخزن ماند. نسل بعدی توسعه (یا خودم در جلسهٔ بعد) لازم نیست دوباره از صفر شروع کند.

محدودیت‌های این گزارش

  • اندازه‌گیری‌ها روی Chromium دسکتاپ با شبیه‌سازی کندسازی انجام شد، نه روی گوشی واقعی کاربر. رفتار مرورگر Safari روی iOS ممکن است کمی متفاوت باشد.
  • هزینهٔ backdrop-filter در Chromium نسبت به Safari سبک‌تر است؛ پس بهبود واقعی روی iPhone احتمالاً بیشتر از اعداد این گزارش است.
  • این گزارش تضمین نمی‌کند کاربر هیچ گاهی گیر نبیند؛ تضمین می‌کند چهار عامل شناسایی‌شده و اثبات‌شده حذف شده‌اند.
